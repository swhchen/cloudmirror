# 云镜推演 · 工程设计说明 v0.3

> 面向云原生系统的**装配台 + 试车台**：在无限画布上把机器、容器、服务、端口按真实约束拼成一套能跑的系统，
> 判它"能不能运行"，再模拟"哪里炸了会波及谁、怎么救最划算"。
>
> v0.3 调整：**多工程并行 / 自绘 SVG 画布 / 校验结果标在画布上 / 多用户预留（暂不做登录）**。
> 依赖由开发方自行补齐，不再等使用方安装。
> 本文档是开工前的工程约定，代码按此实现。

---

## 0. 与已有两套的区别

已有的两套（`CloudMirror-Deduction` / `fault-drill-platform`）都是"先画服务调用图，再注入故障"。
本版分两期，且把"装配"作为第一等公民：

| 期 | 做什么 | 产出 |
| --- | --- | --- |
| **装配期（静态）** | 在无限画布上摆宿主机、容器、服务、中间件，选型号、标端口、连线选接口 | 「可运行性校验报告」：能不能跑、卡在哪、怎么改 |
| **推演期（动态）** | 在通过校验的装配体上注入故障，算传播、算恢复 | 「影响分析 + 恢复方案」 |

第一优先级是**数据模型 + 校验引擎**，页面只做到"能拖、能连、能看结果"，不做花活。

---

## 1. 定位

一句话：**一台能装、能试的云系统模拟器。**

- 装：把 `物理机 / 虚拟机 / 容器 / 应用服务 / 中间件 / 网关 / 外部系统` 按真实拓扑拼起来。
- 试：静态检查端口冲突、CPU 超分、依赖缺失、入口不可达等 12 类问题。
- 演：注入故障，算波及范围、传播路径、恢复代价。
- 补：每一步结论都有原因、有数字、可复现。

适用：高校软件工程实践、云运维培训、中小信息系统故障演练、比赛演示。

## 2. 界面形态：一块无限画布

**打开即是画布，没有登录、没有首页跳转。** 整屏布局：

```
┌──────────────────────────────────────────────────────────────┐
│ 顶部工具条：项目名 ▾（切换/新建/重命名） ｜ 100% ▾ ｜ 适应画布 ｜ ▶ 校验 ｜ ⚡ 注入故障 │
├──────────────┬────────────────────────────────┬──────────────┤
│ 左侧节点库    │                                │ 右侧属性面板   │
│ ─ 物理机      │                                │  名称/类型/型号 │
│ ─ 虚拟机      │        无限画布（可平移缩放）      │  资源四项      │
│ ─ 容器       │        节点 + 接口级连线          │  端口列表      │
│ ─ 应用服务    │        框选、吸附网格、小地图      │  关联连线      │
│ ─ 中间件      │                                │  校验问题定位   │
│ ─ 网关       │                                │              │
│ ─ 外部系统    │                                │              │
│ [搜索框]      │                                │              │
├──────────────┴────────────────────────────────┴──────────────┤
│ 底部状态栏：节点 9 ｜ 连线 12 ｜ 可运行性 88 分（2 警告）｜ 缩放 100%      │
└──────────────────────────────────────────────────────────────┘
```

画布能力：

- **平移**：空白处拖拽 / 空格+拖拽 / 滚轮平移；**缩放**：Ctrl+滚轮或 `+` `-`，10%–300%。
- **拖拽建节点**：从左栏拖到画布任意位置，落点即坐标，自动吸附 8px 网格。
- **连线**：从节点右侧的连接点拖到目标节点 → 弹窗选边类型 → 选接口（源端口 → 目标端口）。
- **框选**：矩形框选多个节点批量移动；右键菜单（删除、复制、查看校验问题）。
- **小地图**：右下角缩略图，节点上百也不会迷路。
- **视图状态持久化**：每个工程记住 `scale / offset_x / offset_y`，刷新回来还是那个视角。

### 2.1 多工程并行

- 顶部项目名下拉：**切换 / 新建 / 重命名 / 复制 / 删除**，可同时开多个工程（如"电商-生产""电商-演练""教务-测试"）。
- 每个工程**完全独立**：一套节点、端口、连线、型号引用、校验记录、故障与推演历史；互不串数据。
- 画布视角、网格吸附开关按工程分别记忆。
- 新建工程时可"从示例导入"（电商 9 节点）或"从另一工程复制"。

## 3. 用户流程（六步）

1. **建工程**：起名（默认"未命名推演"），空画布直接可用。
2. **拖节点**：从左侧节点库拖出宿主机、容器、服务、中间件、网关、外部系统。
3. **选型号 + 标端口**：宿主机选 `4C8G` 自动带出 CPU/内存；服务填端口、暴露范围、宿主机映射端口。
4. **连线选接口**：五类边，`depends_on` 必须指定"源端口 → 目标端口"，例如 `order-svc:8081 → mysql-master:3306`。
5. **一键校验**：出"可运行 / 不可运行"结论 + 12 条规则逐条结果 + 修复建议 + 评分。
6. **推演**：注入故障 → 传播分析（直接/间接、路径、层级、比例）→ 恢复推荐（适用性 + 五维评分）→ 落存历史，可回看导出。

## 4. 领域模型

### 4.1 节点类型 `node_kind`

| 值 | 含义 | 型号决定什么 | 典型资源 |
| --- | --- | --- | --- |
| `host` | 物理机 / 云主机 | 核数、内存、磁盘 | `cpu_cores`、`mem_total_mb`、`disk_gb`、`ip` |
| `vm` | 虚拟机 | 核数、内存、磁盘 | 同上（归属 host） |
| `container` | 容器 | CPU/内存请求（上限） | `cpu_request`、`mem_request_mb`、`runtime` |
| `service` | 应用服务 | 单实例资源需求 | `cpu_request`、`mem_request_mb`、`replicas` |
| `middleware` | 中间件（MySQL/Redis/MQ） | 内存、连接数 | `mem_total_mb`、`port` |
| `gateway` | 网关 / 负载均衡 | 监听端口、并发 | `port` |
| `external` | 外部系统 / 第三方接口 | 域名、端口 | `ip`、`port` |

### 4.2 型号库 `asm_device_model`

节点不必手填资源，从型号库里挑，挑完自动带出参数；**带出后仍可逐项手改**。

| 字段 | 说明 |
| --- | --- |
| `kind` | 适用节点类型（host / vm / container / service ...） |
| `model_name` | 型号名，如 `标准型 4C8G` |
| `cpu_cores` / `mem_mb` / `disk_gb` | 型号固化的资源 |
| `spec_json` | 附加参数（带宽、连接数上限等） |
| `builtin` | 是否内置（内置不可删，可复制成自定义） |

**内置型号（首批）**

| 类型 | 型号 | CPU | 内存 | 磁盘 | 备注 |
| --- | --- | --- | --- | --- | --- |
| host | 入门型 2C4G | 2 | 4 GB | 40 GB | 演示用 |
| host | 标准型 4C8G | 4 | 8 GB | 100 GB | 电商示例默认 |
| host | 计算型 8C16G | 8 | 16 GB | 200 GB | |
| host | 内存型 16C32G | 16 | 32 GB | 500 GB | |
| vm | 2C4G / 4C8G | 2 / 4 | 4 / 8 GB | 40 / 100 GB | |
| container | 迷你 0.5C1G | 0.5 | 1 GB | — | |
| container | 标准 1C2G | 1 | 2 GB | — | |
| container | 大型 2C4G | 2 | 4 GB | — | |
| service | 轻量 1C2G | 1 | 2 GB | — | 副本数默认 1 |
| service | 标准 2C4G | 2 | 4 GB | — | |
| middleware | Redis 2C4G | 2 | 4 GB | 20 GB | 1 万连接 |
| middleware | MySQL 4C8G | 4 | 8 GB | 200 GB | 500 连接 |
| middleware | MQ 2C4G | 2 | 4 GB | 100 GB | 1 千队列 |
| gateway | 网关 1C2G | 1 | 2 GB | — | |
| external | 外部接口 | — | — | — | 无资源 |

**可改规则**

1. 选中型号 → 自动填 `cpu_cores / mem_total_mb / disk_gb`（容器/服务填 `cpu_request / mem_request_mb`）。
2. 手改后：节点字段**以手改为准**，型号只记录"参考来源"，校验只读节点字段。
3. `恢复型号默认` 按钮可一键回到型号值。
4. 改节点**不会**回写型号库；要加自己的规格就在型号库"新增型号"（`builtin=0`），内置型号只读。
5. 型号可以为空（纯手填），此时不显示型号，完全按字段算。

### 4.3 节点属性 `asm_node`

- 布局：`pos_x`、`pos_y`
- 型号：`model_id`（外键，可空）、型号带出的 `cpu_cores`、`mem_total_mb`、`disk_gb`
- 请求：`cpu_request`、`mem_request_mb`（容器/服务用）
- 运行：`ip`、`runtime`（镜像/版本）、`replicas`、`status`
- 展示：`name`（同工程内唯一）、`node_kind`、`description`、`icon`

### 4.4 端口 `asm_node_port`（连线的"接口"就指它）

| 字段 | 说明 |
| --- | --- |
| `port` | 1–65535 |
| `protocol` | `tcp` / `udp` |
| `scope` | `container`（容器内）/ `internal`（内网）/ `public`（对外） |
| `host_port` | 映射到宿主机端口（`scope=public` 必填） |
| `purpose` | 如 `HTTP API`、`MySQL 协议` |

### 4.5 连线 `asm_edge`（五类边 + 接口级端点）

| `edge_kind` | 语义 | 方向 | 接口要求 |
| --- | --- | --- | --- |
| `deploy_on` | 部署于 | 容器/服务 → 宿主机 | 不选接口 |
| `network_link` | 网络可达 | 任意 → 任意 | 可选接口（网络路径两端） |
| `port_map` | 端口映射 | 服务 public 端口 → 宿主机 | **必选**：源为 public 端口，目标为宿主端口 |
| `depends_on` | 调用依赖 | 调用方 → 被调用方 | **必选**：源端口 → 目标端口 |
| `replicate` | 主备复制 | 主 → 备 | **必选**：复制通道端口 |

边上的约束：`source_port_id`、`target_port_id`、`bandwidth_mbps`、`latency_ms`、
`strong`（强/弱依赖，参与传播衰减，弱依赖权重 0.5）、`weight`、`description`。

**为什么必须选接口**：端口冲突（R01/R03）、网络可达（R08）、依赖缺失（R07）都要落到具体端口上，
只连"节点到节点"的话，校验引擎没法判断"这个服务真的能连上那个数据库"。

### 4.6 可运行性校验规则 `R01–R12`

| 编号 | 规则 | 级别 | 判定要点 |
| --- | --- | --- | --- |
| R01 | 端口冲突 | error | 同一宿主机、同协议、同端口被两个节点占用 |
| R02 | 端口越界 | error | `port` 或 `host_port` 不在 1–65535 |
| R03 | 端口映射冲突 | error | 两个 `port_map` 抢同一宿主机端口 |
| R04 | CPU 超配 | error | 宿主机上 `Σ 子节点 cpu_request > cpu_cores × 1.0` |
| R05 | 内存超配 | error | `Σ mem_request_mb > mem_total_mb` |
| R06 | 磁盘超配 | error | `Σ disk_gb > 宿主机 disk_gb` |
| R07 | 依赖缺失 | error | `depends_on` 指向不存在节点/端口，或服务依赖里没有任何 `middleware` |
| R08 | 网络不可达 | error | 有 `depends_on` 但两端不在同一网络分区且无 `network_link` 通路 |
| R09 | 循环依赖 | warn | `depends_on` 有向图存在环（列出环上节点） |
| R10 | 入口不可达 | error | 从 `external`/`gateway` 出发到任一 `service` 无通路 |
| R11 | 孤儿节点 | info | 未参与任何连线的节点 |
| R12 | 主备不完整 | warn | 冗余组缺主/缺备、成员类型不相容、主备端口不一致 |

**判定逻辑**：任一 `error` 未通过 → "不可运行"；仅 `warn`/`info` → "可运行但需关注"。
**可运行性评分** = `100 - 30×错误 - 10×警告 - 2×提示`（下限 0），用于对比修改前后。
每条不通过项必须返回：规则编号、级别、涉及节点/边 ID、中文说明、修复建议，前端可一键定位到画布元素。

## 5. 故障与传播

### 5.1 故障类型

`node_down`、`service_unavailable`、`network_latency`、`network_unreachable`、`port_blocked`、`cpu_saturation`。
严重程度 `low/medium/high/critical`；状态 `active/recovered`。

### 5.2 传播分析（算法①）

- **方向铁律**：边 `A → B` 表示 A 依赖 B；传播方向相反，B 故障 → A 受影响。
- 建反向邻接表 `dependents[B] = [A, ...]`。
- **多源 BFS**：所有激活故障源同时以距离 0 入队，`visited` 防环，首次发现即最短距离。
- 距离 1 = `direct`，≥2 = `indirect`；故障源自身不计入受影响集。
- 路径回溯：BFS 记 `parent`，还原"源头 → … → 目标"完整链路并落库（含接口级端口信息）。
- 多源触达同一节点：取最短距离，同距离按故障 ID 取先者。
- 无随机数、不调大模型，同样输入永远同样输出。

### 5.3 传播增强（按需启用）

| 增强 | 做什么 | 用途 |
| --- | --- | --- |
| E1 传播强度衰减 | 沿路径累乘边权（强 1.0 / 弱 0.5），低于阈值归"潜在波及" | 区分"必崩"与"可能抖" |
| E2 关键单点 | `depends_on` 图割点 | 加固优先级 |
| E3 最小隔离切口 | 近似最小点割集 | 隔离策略的量化依据 |
| E4 多动作恢复序列 | 深度 ≤3 动作组合搜索，比较总时长/成本/二次风险 | 从"推荐一个动作"到"推荐一条路径" |

### 5.4 恢复策略与评分（算法②）

| 策略 | 适用条件 | 恢复时间 | 成本 | 风险 |
| --- | --- | --- | --- | --- |
| `restart_service` | 存在 `node_down`/`service_unavailable` | `120 + 60×节点数` 秒 | 低 | 中 |
| `failover` | 故障主节点属于显式冗余组且组内有合格备用 | `60 + 30×故障数` 秒 | 高 | 低 |
| `isolate_node` | 隔离后用户入口仍保留可用依赖 | `30 + 15×故障数` 秒 | 低 | 低/中 |

权重（合计 1.00）：恢复时间 `0.25`、影响范围 `0.20`、资源成本 `0.15`、操作风险 `0.20`、业务恢复 `0.20`；
参考恢复时间 600 秒；`score = 100 × Σ(权重 × 归一化分项)`。只从适用策略取最高分推荐，
同分按 `restart → failover → isolate` 打破平局；不适用策略展示分数与原因但永不推荐。

### 5.5 冗余校验（算法③）

`failover` 只认显式冗余组，逐个备用节点过闸：无激活故障 → 未被本次分析判为受影响 → 与主节点类型相容
→ 无依赖故障风险 → 优先级明确。任一不过即 `applicable=false` 并说明原因，**绝不虚构备用节点**。

## 6. 数据库设计（MySQL 8）

库名 `cloudmirror`，`utf8mb4`。两张分组：装配期 `asm_*` / `project`，推演期其余。

### 6.1 表清单

| 表 | 说明 |
| --- | --- |
| `project` | 推演工程（含画布视图状态、`owner_id`） |

| `asm_device_model` | 型号库 |

```sql
  warn_count INT DEFAULT 0,
  info_count INT DEFAULT 0,
  summary VARCHAR(500),
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  KEY idx_project (project_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE asm_check_item (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,

```

推演期表（`fault_event`、`propagation_analysis` 及子表、`recovery_*`）在 P2/P3 随代码补全，
字段与第 5 节算法一一对应。

### 6.3 多用户预留（本轮不做登录）

- `project.owner_id` 默认 `0` = 本地默认用户；接登录后存真实用户 ID，所有查询自动带 `owner_id` 过滤。
- `sys_user` 表**现在就建好**（`id / username / password_hash / display_name / created_at`），P5 再接登录，避免以后改表。
- Service 层留 `CurrentUser.id()` 钩子，现在恒返回 `0`，将来换成 JWT 解析，**业务代码不用改**。
- 前端右上角预留用户区，现在显示"本地"。
- 唯一约束按 `(owner_id, name)` 设计，避免不同用户之间项目重名冲突。

### 8.1 工程约定

- Java 17 语言级别，JDK 25 编译运行；**不用 Lombok**（新版 JDK 注解处理器有坑，也便于逐行审查）。
- MyBatis-Plus 注解 + 少量 XML，SQL 可读可改。
- 统一返回 `{ code, message, data }`；分页 `{ items, total, page, size }`。
- `springdoc-openapi`，`/swagger-ui.html` 可点。
- 建库脚本幂等（`CREATE TABLE IF NOT EXISTS` + `INSERT ... ON DUPLICATE KEY UPDATE`），重复执行不毁数据。
- 不提交 `target/`、`node_modules/`、`.env`、日志、数据库文件。
