# 云镜推演 · 8 分钟演示脚本

> 目标：让评委在 8 分钟内看懂「这是什么、怎么算的、凭什么可信」。
> 全程用真实接口，不切假数据；每一步都能现场改数字验证。

---

## 0. 开场前 2 分钟准备

| 检查 | 命令 / 动作 |
| --- | --- |
| 后端 | 双击 `scripts\启动后端-H2.bat`（或 `启动后端.bat` 连 MySQL） |
| 前端 | 双击 `scripts\启动前端-演示.bat`，等浏览器打开 <http://127.0.0.1:4173> |
| AI | 双击 `scripts\启动AI服务.bat`（可选，不开也能演示降级） |
| 备用 | 提前打开两个标签页：画布、<http://127.0.0.1:8080/swagger-ui.html> |

> 如果现场没网：AI 那一步会显示「本地规则（AI 未连接）」，照常讲，反而能体现降级设计。

---

## 1. 一句话开场（30 秒）

> "我们做的不是混沌工程——混沌工程是**真把服务弄挂**。
> 我们做的是**上战场之前的沙盘**：先把系统按机器、容器、端口装起来，判它能不能跑；
> 再模拟故障会波及谁；最后算怎么救最划算。全程确定性、可复现、每条结论都有原因。"

---

## 2. 装配：一张图讲清系统（60 秒）

1. 顶部下拉选工程；空工程就点左侧节点库加几个节点。
2. 指出三类元素：
   - **节点**：宿主机 / 容器 / 应用服务 / 中间件 / 网关
   - **端口**：节点右侧的小圆点，橙色是对外端口
   - **连线**：连线模式下拉（调用依赖 / 部署于 / 网络可达 / 主备复制）
3. 演示一次连线：选「调用依赖」→ 点网关端口 → 点订单服务端口。
4. 强调：**连线是端口到端口**（`8080 → 8081`），不是服务到服务——所以后面能算到接口级。

---

## 3. 校验：判"能不能跑"（90 秒，本场核心之一）

1. 点 **▶ 校验可运行性** → 底部出问题清单，画布上问题节点画红环。
2. 制造一个问题（现场演示）：
   - 选中宿主机 → 看已分配核数；或给某个节点把 CPU 请求改大 → 保存 → 再校验
   - 应看到：`R04 host-a CPU 超配：已分配 4.5 核 / 可用 4.0 核`
3. 点问题条目 → 画布自动定位到该节点（红环）。
4. 修复（把请求改小或换大机型）→ 再校验 → **分数从 70 回到 100**。
5. 一句话总结：
   > "12 条规则、逐条可解释；同一个数字改一下结论就翻转——这不是模型猜的，是算出来的。"

---

## 4. 故障注入与传播（120 秒）

1. 选中 MySQL 主 → 右侧「注入故障」→ 宕机 → 注入。
2. 点 **◎ 推演分析**：
   - 画布：订单服务橙色（直接）、网关黄色（间接）
   - 面板：`1 个故障源波及 2 个节点（直接 1 / 间接 1；必崩 1 / 可能 1）`
   - 路径：`MySQL主 → 订单服务 → 网关`
3. 讲算法（15 秒）：
   > "边 A→B 表示 A 依赖 B，传播方向相反；多源 BFS 一遍扫完，记录父边回溯路径；
   > 传播强度 = 边权 × 宿主机容量余量放大，≥0.6 判必崩。"
4. 点 **🕘 历史** → 展示这次推演已落库，能回看快照。

---

## 5. 恢复决策（90 秒）

1. 点 **✚ 恢复方案**：
   - 三张卡：服务重启 / 备用节点切换 / 故障节点隔离
   - 展示评分明细（时间 .25 / 影响 .20 / 成本 .15 / 风险 .20 / 业务恢复 .20）
   - 推荐：切备 85.75 > 重启 84.5 > 隔离 50.79（不适用）
2. 点 **⌁ 增强分析**：
   - 关键单点：订单服务（依赖图断成 N 块）
   - 隔离切口：可达 2 → 0
   - 恢复序列：`切备 MySQL主(60s)`，次优 重启(120s)、隔离(300s)
3. 讲取舍（20 秒）：
   > "隔离最快（30 秒），但它会把节点永久下线，所以风险权重设成 8 倍，
   > 不可能靠'快'赢——这是模型在讲道理，不是排序。"

---

## 6. AI 辅助诊断（60 秒）

1. 点 **✦ AI 诊断** → 底部面板出结构化诊断（根因 / 影响 / 建议 / 风险提示）。
2. 讲设计（20 秒）：
   > "三层降级：大模型 → AI 服务规则 → 后端本地规则。
   > 没配 Key、没网、服务挂了，页面都照样有输出，不会白屏。"

---

## 7. 收尾与技术底色（60 秒）

三句话：

1. **确定性**：无随机数、无模型参与判定，同样输入永远同样输出，可以现场连跑。
2. **可解释**：每条问题带规则编号、具体数字、修复建议；每个策略带五项评分。
3. **诚实边界**：这是**建模校验/推演**，不是真实探测；不执行真实切流、不校验真实容量与网络。

再加一句差异化：
> "市面上混沌工程是真注入；APM 是看真实流量；我们做的是**赛前沙盘**，三者互补。"

---

## 8. 备用方案（现场出问题怎么办）

| 故障 | 应对 |
| --- | --- |
| 前端打不开 | 换 <http://127.0.0.1:5173> 或直接用 Swagger 演示接口 |
| AI 服务没起 | 照常点，显示"本地规则（AI 未连接）"，讲降级设计 |
| 数据库坏了 | 用 H2 模式（`启动后端-H2.bat`），数据在 `backend/data/` |
| 端口被占 | 改 `application.yml` 的 `server.port`，或重启电脑 |
| 演示中途崩 | 打开 `docs/screenshots/` 里的截图兜底讲解 |

## 9. 评委高频提问（预演答案）

| 问题 | 回答要点 |
| --- | --- |
| 和 Chaos Mesh / ChaosBlade 有什么区别？ | 它们真注入、我们是沙盘推演；先判可运行性，再算影响与恢复；不弄挂任何东西 |
| 多源 BFS 是你们发明的吗？ | 不是，BFS、割点、最小割都是成熟算法；我们的工作是**组合成可解释决策链** + 容量感知 + 接口级粒度 |
| 数据真实吗？ | 拓扑是建模数据，结论由规则算出；边界写进文档：不校验真实容量/网络/数据同步 |
| 为什么不用 K8s？ | 演示环境无集群；系统设计成与平台无关，真实接入只需替换数据源 |
| 能处理多大拓扑？ | 500 节点/1000 边单次校验约 1.6ms，有性能基准测试 |
| 恢复方案凭什么可信？ | 五维加权、权重写死可查、每项都有分项得分；不适用策略永不推荐 |
| AI 会不会瞎编？ | AI 只做解释，不参与判定；三层降级，离线也有规则输出 |
